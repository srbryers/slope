**Changes requested.** S242-2 (formatter) and S242-3 (statusCommand) are correct. ## Findings

### F1 — MAJOR — Enriched generated reviews are silently clobbered (marker persists through human edits)

`src/cli/commands/review.ts:124` — the refusal fires only when `!existing.includes(REVIEW_GENERATED_MARKER)`. Once slope has generated a review, the marker stays in the file forever, so **any subsequent human/agent enrichment of that file is unprotected**: the next `slope review` run overwrites it silently (exit 0, no warning), confirmed by the code path and by the test "Marker-carrying file regenerates freely on a later run".

This defeats the feature's own companion mechanism. The intended `reviewRequiredSections` workflow is: gate demands `## What went wrong` → agent appends it to the generated review (marker still on line 1) → gate closes. The documented post-hole flow then runs `slope review findings add` → `slope review amend` → re-run `slope review` to regenerate — which **wipes the appended sections**. The gate check then reports them missing (and per F4 the gate may silently stay closed anyway). Recovery only via git.

- **Failing input:** file = `<!-- generated by slope review -->\n\n## Sprint 130 Review…\n## What went wrong\n<human text>\n`; run `slope review` → `## What went wrong` destroyed, no refusal.
- **Required fix:** protect *modified* content, not *unmarked* content. Embed a content hash in the marker (e.g. `<!-- generated by slope review sha256:<hash-of-body> -->`); overwrite freely only when the hash matches the file body, otherwise refuse without `--force`. This also fixes F2.

### F2 — MAJOR — Project-authored files that merely quote the marker are misclassified as generated

`src/cli/commands/review.ts:124` — `includes()` matches the marker anywhere. A hand-authored review that quotes the marker string — a retro discussing this very feature, a doc showing slope output, a code fence — is treated as slope-generated and **silently overwritten** without `--force`. This repo dogfoods slope and writes retros about slope features, so it is the most likely victim.

- **Failing input:** authored `sprint-N-review.md` containing the sentence: "slope now writes `<!-- generated by slope review -->` at the top of generated files." → next `slope review` run replaces the whole file, exit 0.
- **Required fix:** at minimum anchor the check (`existing.startsWith(REVIEW_GENERATED_MARKER)`); the F1 hash-marker approach subsumes this.

### F3 — MEDIUM — repairMojibake is asymmetric: right double quotes and ellipses stay mangled

`src/cli/commands/review.ts:72-79` — the table repairs left double quote (`â€œ`, cp1252 0x9C) but not right double quote: U+201D is UTF-8 `E2 80 9D`, and 0x9D is unmapped in cp1252 (decodes to control U+009D), so the mojibake is `â€` and no pattern matches it. Same for ellipsis `â€¦` (U+2026 → `E2 80 A6`, 0xA6 = `¦`) and bullet `â€¢`.

### F4 — MEDIUM — review_md gate is never re-opened when the on-disk review becomes non-compliant

`src/cli/commands/review.ts:158-163` — the missing-sections branch only prints "gate left open"; `updateGate(cwd, 'review_md', false)` is never called. If the gate was already `true` from an earlier compliant run and the review is then regenerated without the sections (`--force`, or the F1 wipe), the gate silently stays closed and closeout proceeds against a non-compliant review — the message even lies ("left open") when the gate is in fact closed.

- **Failing sequence:** compliant review on disk → `slope review` closes gate → `slope review --force` (or amend/regenerate) replaces it with a generated review lacking the sections → stderr says "gate left open" but `gates.review_md` remains `true`.
- **Fix:** in the missing branch, explicitly `updateGate(cwd, 'review_md', false)` (and adjust the message), or at least detect and warn that the gate was previously closed.

### F5 — LOW/MEDIUM — `--stdout` closes the gate against content that is not on disk

`src/cli/commands/review.ts:113-114` — `reviewOnDisk` is initialized to the freshly generated review and, on `--stdout` (outputPath === null), the write block is skipped entirely, so the gate validates content that exists nowhere on disk. The comment "whatever ends up on disk" is false for this path. Consequences:

1. With no `reviewRequiredSections`, `slope review --stdout` sets `review_md = true` with **no review file anywhere**. This is behavior-parity with main (main called `updateGate` unconditionally), so not a regression — but the sprint is titled "closeout integrity" and the new code now codifies the fiction.
2. With sections configured and a *compliant authored file already on disk*, `--stdout` validates the generated (section-less) content instead and leaves the gate open despite a compliant review existing. Wrong direction is conservative, but inconsistent with the refusal path, which validates the disk file.

- **Fix:** on stdout-only runs, either skip the gate update, or read and validate the default-path file if it exists.

### F6 — LOW — repairMojibake rewrites content that intentionally quotes mojibake

Repair now runs at the source on the whole review, so a scorecard note that *quotes* mojibake (e.g. an S242 shot note: "fixed the `â€”` artifacts in reviews") is silently rewritten to "fixed the `—` artifacts" in both stdout and the file — the quoted evidence no longer says what the author wrote. This repo's own #616/S242 retro notes are the most likely input. The stderr note ("repaired cp1252-mangled character sequences") is the only signal. Acceptable tradeoff, but document it; there is no opt-out flag.

### F7 — LOW — required-sections match is an unanchored substring over the whole document

`src/cli/commands/review.ts:159-160` — `haystack.includes(section.toLowerCase())` matches prose or code fences, not just headings. A review containing the sentence "the ## What went wrong section is still TODO" (or a fenced example) closes the gate without the heading existing. Suggest a per-line anchored match (`/^\s{0,3}#{1,6}\s*.../` against each line) since the config documents these as "section headings".

### F8 — INFO — Migration behavior change: all pre-S242 generated reviews now refuse to regenerate

Reviews generated before this release carry no marker, so they are indistinguishable from project-authored files: the first `slope review` re-run in every existing project refuses and requires `--force`. Probably the right conservative default, but it needs a changelog note. Also note the refusal exits 0 (intentional, since the gate is still honored) — automation checking only exit codes will not notice that content was not refreshed.
