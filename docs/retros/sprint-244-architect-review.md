# Sprint 244 — Architect Review

**Reviewer:** workflow-architecture-reviewer (architect lane, independent)
**Branch:** `feat/S244-session-wrap-standup` vs `main`
**Scope:** #619 (standup substance, transcript negative durations), #620 (wrap-session skill, session end default)
**Date:** 2026-07-16

## Verdict

**APPROVE WITH REQUIRED FIXES** — the layering is right (CLI gathers, core stays pure and renders), the transcript duration fix is correct, and backward compatibility of `StandupReport` is preserved. But the diff regresses on the codebase's `execFileSync` convention with a real injection surface, the session-end default has a concrete multi-agent footgun via the installed session-end hook, `parseStandup` silently drops the new `context` field on round-trip, and the pi skill template is missing the frontmatter every other pi skill carries.

## Findings

### F1 — MEDIUM (security / convention): shell interpolation of store data into `execSync`

`src/cli/commands/standup.ts:45-48`

```ts
const log = execSync(
  `git log --oneline --since=${JSON.stringify(sessionStartedAt)}`, ...
```

`JSON.stringify` produces a double-quoted shell string. In POSIX shells, `$(...)` and backticks **still expand inside double quotes**, and `JSON.stringify` does not neutralize `$` or backticks. A `started_at` value of `2026-01-01$(rm -rf ~)` executes on the next `slope standup`.

Today `started_at` is generated by `registerSession` (`src/store/index.ts:401-405`) as `nowISO()`, so the value is slope-controlled in normal operation. But `.slope/slope.db` is a plain repo-local SQLite file: cloning an untrusted repo that ships a poisoned db and running `slope standup` executes attacker shell. This is exactly the class the newer modules eliminated — `src/cli/workflow-resync.ts:52,340`, `src/cli/actor.ts:59-65`, `src/cli/sprint-resume.ts:80-112`, `src/core/flows.ts:148`, and `src/mcp/index.ts:453-693` all use `execFileSync('git', [args])`. Note this diff *already imports from* `workflow-resync.ts`, whose first function is the `execFileSync` pattern to copy. (The legacy `execSync` calls in `git-utils.ts` are static commands, not interpolations — they are not precedent for this.)

**Required fix:** `execFileSync('git', ['log', '--oneline', `--since=${sessionStartedAt}`], { cwd, ... })`, and use the same form for the `rev-parse` call for consistency.

### F2 — MEDIUM (multi-agent safety): single-active default can end a teammate's session via the installed hook

`src/cli/commands/session.ts:176-192`

The installed session-end hook is `slope session end --session-id="$SLOPE_SESSION_ID"` (`src/cli/commands/init.ts:839`, `doctor.ts:426`, `hook.ts:22`). When the env var is unset, the arg expands to `--session-id=` — and `parseArgs` (`session.ts:11`, regex `=(.+)`) drops empty-valued flags entirely. Pre-sprint that invocation failed harmlessly ("--session-id is required"). Post-sprint it falls through to the single-active default and ends **whatever** single session is active — including a live teammate's in a same-checkout swarm (shared `.slope/slope.db`), silently releasing that agent's claims. `removeSession` cascades claim deletion, so the teammate's claim-required guard state is destroyed from under them.

Compounding: `getActiveSessions` (`src/store/index.ts:472-475`) returns **all** session rows with no heartbeat filter, so the "single active session" may equally be a stale crash leftover from a different worktree/branch — ending it is fine, but the code cannot tell the two cases apart.

**Required fix:** before accepting the single-active default, verify the session plausibly belongs to this context — `worktree_path` matches `cwd` and/or `branch` matches the current git branch (sessions store both). If it doesn't match, keep the old error and print the session details. Alternatively (or additionally): only apply the default when the session's `last_heartbeat_at` is stale **or** the identity check passes. The printed "Defaulting to..." line is good but is not a safeguard in hook context where nobody reads stdout.

### F3 — MEDIUM (data integrity): `parseStandup` drops `context` on round-trip

`src/core/standup.ts:216-232`

`generateStandup` now embeds `context` and the CLI stores the full report as the standup event's `data`. But `parseStandup` reconstructs the report field-by-field and omits `context`. Consequences:

- `slope standup --aggregate` (`standup.ts:127-132`) parses stored events, so `TeamStandup.agents[]` — including `--aggregate --json` output — silently loses the context that was persisted.
- `slope standup --ingest` produces an in-memory report without context (the raw event data keeps it, masking the loss).
- Any future consumer that re-`formatStandup`s a parsed report renders no context block, defeating #619 for exactly the multi-agent aggregation path standups exist for.

**Required fix:** add `context: data.context as StandupContext | undefined` (or a small validator) to `parseStandup`. Consider a follow-up to surface per-agent context in `formatTeamStandup` (e.g. branch per agent) — that is where the swarm value is.

### F4 — MEDIUM (template correctness): pi skill template missing YAML frontmatter

`templates/pi/skills/wrap-session.md:1`

Every other pi skill (`start-sprint.md`, `post-sprint.md`, `review-pr.md`) opens with `--- name / description ---` frontmatter; `init.ts` installs these as `.pi/skills/<name>/SKILL.md` explicitly "per the Agent Skills spec" (`init.ts:804-806`), which requires `name` and `description` frontmatter for skill discovery. The new file is a byte-identical copy of the claude-code command and has none — pi skill discovery/triggering for wrap-session is likely broken or degraded. (The claude-code variant correctly matches its siblings, which have no frontmatter.)

**Required fix:** add frontmatter to the pi variant, e.g. `name: wrap-session`, `description: Session-close routine — standup wrap, unpushed-work check, claim release, handoff summary.` The two files should stop being identical; that they currently are is a hint the pi variant wasn't checked against its neighbors.

### F5 — LOW (duplication): transcript duration logic now lives in two places

`src/cli/commands/standup.ts:63-78` and `src/cli/commands/transcript.ts:213-226`

The #619 min/max-valid-timestamp scan is implemented twice, character-for-character in spirit. Next timestamp edge case gets fixed in one and not the other. `readTranscript` already lives in `src/core/transcript.ts` — extract a `transcriptTimeSpan(turns)` / `transcriptDurationMin(turns)` helper there and consume it from both call sites.

### F6 — LOW (consistency): `context.sprint` can disagree with the stored event's `sprint_number`

`src/cli/commands/standup.ts:30` resolves the display sprint as `sprintNumber ?? inferSprintContext(...)` (branch-name inference), while the event is stored under `sprintNumber ?? config.currentSprint ?? 1` (`standup.ts:203,224`). When the branch says S244 but config says S243, the standup *displays* one sprint and is *aggregated* under another. Resolve the sprint once and use it for both the context block and `insertEvent`.

### F7 — INFO (accepted): notes, non-blocking

- **Layering:** correct. All I/O (git, fs, sprint inference) is in the CLI layer; `generateStandup`/`formatStandup` remain pure and testable; `StandupContext` optional on `StandupReport` keeps old stored events parseable. This matches the repo's core/CLI split.
- **Event bloat:** none — context adds ~200 bytes per standup event; `commits.latest` is bounded by a commit subject.
- **Commit count accuracy:** `git log --since` on HEAD counts any commit whose commit date falls in the window, including commits pulled in from others mid-session — acceptable for a wrap summary; worth a one-line comment so nobody treats it as authoritative.
- **Template accuracy:** wrap-session.md's claim that `slope session end` defaults to the single active session is true *after* this sprint (correct ordering — the template ships in the same PR as the behavior). Referenced commands (`slope standup`, `slope sprint status`, `slope status`) all exist. Structure/tone matches `post-sprint.md`. One nit: step 1 implies `slope standup` always yields the rich context; every probe is best-effort, so a degraded standup (no git, no transcript) still succeeds — fine, but the skill could tell the agent to fall back to `git log` manually when the branch line is absent.
- **transcript.ts fix:** correct — non-finite timestamps skipped, `latest > earliest` guard prevents negatives and zero-turn/singleton NaN; the unordered-timestamp test covers the #619 repro.
- **session-end tests** (`tests/cli/commands/session-end.test.ts`) cover all four branches of the new precedence including env-var priority — good. Missing: the F2 scenario (empty `--session-id=` from a hook with a foreign active session) — add a test once F2's identity check lands.
